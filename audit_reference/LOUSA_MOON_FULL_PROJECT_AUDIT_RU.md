# LOUSA MOON 1.17.0 - полный аудит проекта

**Проверенная база:** `LOUSA_MOON_V1.17.0_BRAND_TRUST_REBUILD_RC`  
**Архитектурное ограничение:** это mobile-only проект. Фронтенд админ-панели остается отдельной программой. Общий backend и API-контракты для отдельной админ-панели допустимы и проверялись, но исходников admin UI внутри мобильного проекта нет.

> **Честный статус проверки:** выполнен глубокий статический, инженерный и продуктовый аудит исходников. Проверены все 25 файлов маршрутов и layout, общие UI-компоненты, стили, Zustand-хранилища, расчет цикла, анкета, Box, карта, доставка, Prisma-схема и backend endpoints. Автоматически проиндексировано 309 интерактивных объявлений. Старые реальные скриншоты Samsung использованы как визуальное доказательство предыдущих проблем. Последний APK версии 1.17.0 в этой среде не собирался и не запускался, поэтому я не утверждаю, что каждый пиксель и каждое касание уже проверены на последней версии устройства.

## 1. Главный вывод

У LOUSA MOON сильная продуктовая идея: приложение не ограничивается календарем, а соединяет отслеживание цикла, персональный LOUSA Box и бесплатную доставку, включенную в тариф. В проекте есть не пустые макеты, а реальные Firebase/auth-слои, MapLibre, сервисы прогнозирования, API, Prisma-модели, заказы, платежные структуры, доставка, поддержка и локализация.

Однако текущая версия **не готова к публичному production-релизу**. Основные проблемы уже не в цветах. Они находятся в правдивости данных, завершенности бизнес-процессов и общей сложности UX.

Самые опасные дефекты:

1. Анкета может создать подтвержденное начало менструации 13 дней назад, даже когда пользователь выбирает «Добавлю позже».
2. Внутренний store отдельно хранит выдуманный `lastPeriodStart` 13 дней назад при отсутствии записей.
3. Подписка и заказ создаются локально, без завершенного серверного потока quote -> order -> payment -> subscription.
4. Экран утверждает, что цена проверяется сервером, хотя мобильный сценарий не получает обязательный server quote.
5. Настройки сообщают о «защищенном локальном хранилище» данных цикла, хотя крупные health/address данные находятся в AsyncStorage без шифрования содержимого.
6. «Luna assistant» не является AI: это набор регулярных выражений и заранее написанных ответов с искусственной задержкой 450 мс.
7. Качество физических товаров Box нельзя подтвердить по текущей модели: отсутствует полноценная трассировка поставщика, партии, срока годности, входного контроля и отзыва.
8. Проект не проходит текущий lint и один unit-тест.
9. Последняя версия не имеет подтвержденного Device QA, настоящего платежа и живой проверки mobile -> PostgreSQL -> отдельная admin-panel.

**Общая оценка текущего продукта и кода: 4,6/10.**  
**Потенциал после закрытия P0/P1: 8,5-9/10.**  
**Текущая готовность к production: 3,5/10.**

## 6. Общий UX и дизайн

### 6.1 Что уже хорошо

- Палитра стала спокойнее и взрослее.
- Есть общие карточки, кнопки, layout-компоненты и design tokens.
- Основные четыре tab понятны по смыслу.
- Карта визуально и технически является одной из наиболее сильных частей.
- Прогноз теперь чаще обозначается как прогноз, а не факт.
- Mobile/admin frontend разделены правильно.
- Есть reduced-motion/haptic инфраструктура.

### 6.2 Почему приложение все еще ощущается сложным

1. Один экран часто решает четыре-шесть разных задач.
2. Основные и второстепенные карточки имеют одинаковый визуальный вес.
3. Одни и те же объяснения прогноза повторяются на нескольких экранах.
4. Есть скрытые маршруты, которые создают дублирующие пути.
5. Часть данных сохраняется сразу, часть только кнопкой Save.
6. Локальный draft, серверный факт и операционный статус выглядят слишком похоже.
7. Большие экраны трудно поддерживать: login 2200 строк, address 987, cycle 681.
8. Премиальность пытается создаваться количеством карточек и декоративных элементов, хотя доверие создается ясностью и правдивостью.

### 6.3 Проверка каждой кнопки и каждой линии

Я не ограничился визуальной оценкой скриншотов. Из AST/JSX был собран инвентарь из 309 интерактивных объявлений: файл, строка, компонент, отображаемый текст и props. Это позволяет видеть реальные кнопки, PressScale, PrimaryAction, Tabs.Screen и интерактивные строки.

Статический анализ размеров обнаружил 45 вероятных интерактивных целей меньше 48 dp. Android рекомендует не менее 48x48 dp для каждого фокусируемого интерактивного элемента. В проекте только два явных применения `hitSlop`, поэтому большинство найденных кандидатов необходимо увеличить или подтвердить нативным измерением. [4]

Примеры:

- активная tab capsule - 40x30 dp;
- календарный день - 36x36 dp, ячейка 42 dp;
- стрелки календаря - 42 dp;
- profile photo badge - 30 dp;
- support refresh - 36 dp;
- map settings - 36 dp;
- period flow chips - 40 dp;
- period counter buttons - 42 dp;
- множество chips/actions - 40-46 dp.

Полный список находится в `LOUSA_MOON_TOUCH_TARGET_CANDIDATES.csv`.

### 6.4 Главные системные улучшения UI

- Один экран - одна главная задача.
- Не больше одного primary CTA в основном viewport.
- Не больше трех основных блоков до первой прокрутки.
- Убрать карточку внутри карточки там, где достаточно секции.
- Визуально разделять: подтверждено пользователем, предварительный прогноз, общий материал, локальный draft, серверный статус.
- Унифицировать высоту всех интерактивных целей до 48-56 dp.
- У каждой icon-only кнопки должны быть `accessibilityRole`, `accessibilityLabel`, `accessibilityHint` и выбранное состояние.
- Критический текст нельзя уменьшать через `minimumFontScale` до плохо читаемого размера.
- Ошибка и успех должны быть озвучены TalkBack и получать фокус.
- Serif оставить только для рекламы и editorial, но не для рабочих форм.

## 7. Детальный аудит каждого экрана

### 7.1 Startup и root layout

`app/_layout.tsx` одновременно отвечает за routing, шрифты, гидратацию, startup guard и fallback. При ошибке пользователь может получить технические детали и stack trace. Для production нужен спокойный recovery-screen:

- короткий заголовок;
- сохранены ли данные;
- Retry;
- безопасный код ошибки;
- очистка локального кэша только после подтверждения;
- переход в поддержку.

Сырые stack traces не должны показываться пользователю.

### 7.2 Нижняя навигация

Четыре основных раздела выбраны правильно: Сегодня, Цикл, Для тебя, Box. Старый `translateY` активной иконки убран, что хорошо. Но видимая capsule 40x30 dp. Визуальный фон может оставаться компактным, а touch/semantics container должен быть не меньше 48x48 dp.

Проверить на устройстве:

- одинаковый baseline всех иконок;
- одинаковый baseline подписей;
- selected state в TalkBack;
- 360 dp и длинные армянские подписи;
- font scale 150%;
- gesture navigation и трехкнопочная Android-навигация;
- отсутствие перекрытия нижнего контента.

### 7.3 Сегодня

Экран на 449 строк и 11 действий пытается быть одновременно:

- ежедневным статусом;
- прогнозом;
- лунным экраном;
- дневником самочувствия;
- объяснением confidence;
- Box planner;
- feedback-поверхностью.

Это разбивает внимание. Первый viewport должен отвечать только на три вопроса:

1. Что известно сегодня?
2. Нужно ли мне что-то отметить?
3. Что происходит с ближайшим Box?

Целевая структура:

- одна status-card;
- одна основная кнопка;
- компактная Box/delivery summary;
- ниже - необязательное самочувствие.

Луна должна оставаться фирменным визуальным элементом, но не стоять так, чтобы восприниматься медицинской причиной фазы цикла.

### 7.4 Календарь цикла

Положительные стороны:

- подтвержденные данные и прогноз являются разными сущностями;
- confidence понижается при отсутствии подтверждения;
- овуляция не должна считаться подтвержденной;
- нет старой modulo-логики, превращавшей длинную задержку в новый выдуманный цикл.

Проблемы UX:

- файл 681 строк и 19 интерактивных элементов;
- календарь, легенда, быстрые действия, симптомы, история и объяснение прогноза находятся слишком близко;
- небольшие ячейки и маркеры;
- несколько значений могут конкурировать внутри одного дня;
- не всегда ясно, что сохранилось сразу, а что требует Save.

Целевая структура:

- календарь как главный объект;
- выбранный день открывает bottom sheet;
- одно действие «Отметить, что произошло»;
- короткая легенда;
- «Почему такой прогноз?» открывает подробности;
- история и аналитика вынесены глубже.

### 7.5 Для тебя

Сейчас раздел частично дублирует Сегодня, Wellness и Analytics. Общие материалы могут выглядеть как персональная рекомендация. Это рождает ощущение фейковой персонализации.

Найден реальный dead route: три локализации отправляют пользователя на `/screens/privacy`, но такого route нет. Настройки используют правильный путь `/screens/legal?document=privacy`.

Целевой раздел:

- одна персональная мысль;
- почему она показана;
- один следующий шаг;
- один проверенный общий материал;
- отдельная маркировка «Общая информация», если материал не рассчитан по данным пользователя.

### 7.6 Box dashboard

Главная проблема - локальный order state способен выглядеть как реальная операционная доставка. Progress, подготовка и статус должны приходить только с сервера. Локальное состояние без server ID должно называться «Черновик».

Убрать повторяющиеся карточки планирования. Главный экран Box должен показывать:

- активный тариф;
- ближайший подтвержденный Box;
- состав;
- серверную дату/окно;
- подтвержденный адрес;
- «Доставка включена в тариф»;
- одно действие «Управлять Box».

### 7.7 Лунный центр и Wellness

Лунная эстетика соответствует бренду, но в медицинском контексте нужно постоянно сохранять границу: фаза Луны - астрономическая/символическая информация, не механизм менструального прогноза.

Wellness скрыт из tab bar, но открывается из других разделов. Это создает второй путь для тех же дневных записей. Нужен один владелец задачи «Отметить самочувствие».

### 7.8 Авторизация

`app/auth/login.tsx` - 2200 строк и 46 интерактивных элементов. В одном компоненте живут:

- welcome;
- sign-in;
- sign-up;
- email verification;
- phone flow;
- code flow;
- password reset;
- provider-specific состояния;
- legal/consent;
- язык.

Это главная зона регресса. Необходимо разделить на typed auth state machine и небольшие экраны. У каждого provider должны быть свои copy и ошибки. Terms и Privacy должны быть отдельными нажимаемыми ссылками. Любые dev OTP/hints должны удаляться из release bundle compile-time проверкой.

### 7.9 Onboarding/первая анкета

Это критически слабый экран.

Фактический дефект:

- `selectedDate` по умолчанию = сегодня минус 13 дней;
- если пользователь не добавил дату и нажал Continue, код записывает эту дату;
- Finish снова использует ее как fallback;
- запись сохраняется с `confirmed: true` и `source: user`.

Таким образом, «Добавлю позже» фактически создает несуществующую менструацию.

Дополнительные проблемы:

- хранится максимум две даты через `slice(-2)`;
- одного-двух циклов недостаточно для устойчивой уверенности;
- модель знает `postpartum`, `breastfeeding`, `perimenopause`, recent contraception, но onboarding всегда записывает `natural` и `none`;
- цели почти не меняют дальнейший опыт;
- согласие объединяет обработку чувствительных данных и предупреждения о прогнозах;
- sync с backend идет через `Promise.allSettled`, сбои не показываются;
- draft хранится в обычном AsyncStorage;
- это не полноценная анкета персонализации физического Box.

Что должно быть:

- `selectedDate = null`;
- Skip создает ноль period records;
- безопасный путь «Не помню / пока не было / не хочу добавлять»;
- опциональный ввод 3-6 прошлых начал;
- короткие вопросы про гормональную контрацепцию, postpartum, breastfeeding, pregnancy/perimenopause;
- отдельные версии consent;
- явный sync status.

### 7.10 Карта и адрес

Fullscreen Map Picker является сильной частью:

- центральный прицел;
- поиск;
- debounce reverse geocoding;
- sequence guards против старого ответа;
- мое местоположение;
- ручной fallback.

Проблема - основная форма адреса на 987 строк и 36 действий. Она смешивает:

- карту;
- контакт получателя;
- адрес;
- тип помещения;
- подъезд/этаж/квартиру;
- доступ;
- handoff;
- комментарий;
- приватность;
- ошибки backend.

Нужно два этапа:

1. Точное место: карта, поиск, pin, подтверждение.
2. Детали доставки: получатель, телефон, помещение, вход, handoff, комментарий.

Любое изменение улицы/дома после проверки точки должно делать адрес непроверенным до повторного подтверждения. Текст и координаты не могут расходиться молча.

### 7.11 Luna assistant

Код `responseFor()` ищет ключевые слова через регулярные выражения и возвращает заранее написанный ответ. `setTimeout(450)` имитирует печать. Это не AI и не персональное рассуждение.

Риск очень высокий: wellness-приложение показывает пользователю псевдоперсональный «ассистент», который не имеет источников, clinical triage, moderation или безопасной эскалации.

Решение:

- убрать из production;
- либо переименовать в «Справочник LOUSA»/«Помощь по приложению»;
- явно сказать, что ответы заранее подготовлены;
- не отвечать на медицинские вопросы;
- для будущего AI сначала создать источники, safety rules, red-team tests и путь к специалисту.

### 7.12 Analytics, дневные записи и уведомления

Данные собираются подробно, но taxonomy и шкалы расходятся между Wellness и Log State. Это снижает качество аналитики.

Для каждой метрики нужны:

- единая схема;
- одинаковая шкала;
- sample count;
- период анализа;
- версия алгоритма;
- confidence;
- возможность увидеть исходные записи.

Private notifications - хорошая идея, но ее нельзя считать доказанной без проверки lock screen на реальных Samsung/Android версиях.

### 7.13 Редактор периода

Плюсы:

- можно менять даты;
- указывать flow по дням;
- leakage/количество;
- удалять;
- есть Undo-идея.

Критические пробелы:

- нет одного общего валидатора для всех путей записи;
- возможны будущие и пересекающиеся периоды через альтернативные команды;
- end date может создавать очень длинный период;
- при изменении диапазона могут остаться flow/notes вне нового диапазона;
- `period_day` и `period_end` могут оказаться без содержащего period record;
- удаление start/no bleeding может неожиданно затронуть весь период;
- удаление end может превратить запись в ongoing;
- не везде доказан backend sync;
- нет защиты от выхода с несохраненными изменениями.

Нужна одна функция `validateAndNormalizePeriodRecord()` на UI, store и API уровне.

### 7.14 Profile и Settings

Profile содержит правильные категории, но:

- edit photo badge 30 dp;
- часть privacy/settings действий дублируется;
- неясно разделение локальной очистки и серверного удаления аккаунта.

Settings содержит критический trust defect:

- текст утверждает, что cycle data находится в защищенном локальном хранилище;
- фактически `secureDataStore.ts` оборачивает AsyncStorage;
- очередь sync, cycle queue, onboarding draft и address draft также используют AsyncStorage;
- экран показывает старую версию `1.13.2 Build 90` при проекте 1.17.0.

Нужно:

- честно описывать, что защищено сейчас;
- перенести health/address data в зашифрованную БД/хранилище;
- получать version/build динамически;
- разделить «Очистить данные на этом устройстве» и «Удалить аккаунт и серверные данные»;
- server export должен включать реальные серверные данные, а не только локальный JSON.

### 7.15 Анкета Box и checkout

Экран имеет 28 интерактивных элементов и объединяет:

- выбор тарифа;
- product type;
- количество;
- applicator;
- ночь/крылышки/чувствительность/аромат;
- reusable;
- heat pad/tea/chocolate;
- аллергии;
- адрес;
- review;
- consent;
- активацию.

Главный технический дефект:

- расчет выполняется локальной `calculateBoxQuote()`;
- вызывается локальный `box.subscribe()`;
- локальному order присваивается `awaiting_payment` и note `server_quote_required`;
- реальный server quote/order/payment при этом не создается.

Интерфейс говорит, что цена будет проверена сервером, но текущая кнопка подтверждения этого не делает.

Правильная цепочка:

1. Сохранить Box profile на сервер.
2. Получить server quote с catalog/price/stock version.
3. Показать состав, included, paid extras, one-time/recurring, delivery=0 и expiration.
4. Создать order по quote ID и idempotency key.
5. Создать/подтвердить реальный payment intent.
6. Активировать subscription только после authoritative ответа.
7. Показывать logistics только из server events.

### 7.16 Support, Legal и UX Lab

Support имеет реальную модель ticket, но экран на 331 строку перегружен. Нужны понятные SLA, статус, категория, связь с конкретным заказом и отдельная emergency/medical disclaimer логика.

Legal должен иметь versioned документы и запись принятой версии.

`ux-lab` - внутренний инструмент. Он не должен просто быть скрыт; production route manifest должен физически исключать его.

## 8. Механика отслеживания месячных

### 8.1 Что сделано правильно

- Факты и прогнозы являются разными типами данных.
- Используются median/variation/weighted values, а не random.
- Длинная задержка не превращается modulo-логикой в новый правдоподобный цикл.
- Овуляция и фертильное окно блокируются при недостатке истории.
- Пропущенное прогнозное окно может снижать confidence.
- Копирайтинг предупреждает, что расчет не является контрацепцией.

Это правильное направление. ACOG рассматривает характеристики менструального цикла как важный показатель здоровья, но календарный расчет не должен выдавать диагноз. NHS отдельно указывает, что приложения и устройства для определения фертильных дней не имеют официальной рекомендации NHS. Регулируемый FDA Natural Cycles для контрацепции использует не только даты, но и базальную температуру, информацию о менструациях и опциональные тесты. [1][2][3]

### 8.2 Критические дефекты данных

1. Выдуманная первая дата в onboarding.
2. Выдуманный `lastPeriodStart` в store.
3. Нет универсальной проверки будущих дат.
4. Нет универсальной проверки пересечения периодов.
5. Возможны orphan observations.
6. Очень длинный период может сохраниться, а UI показать только часть.
7. После изменения диапазона могут остаться старые дневные детали.
8. Ongoing period может отображаться неполно.
9. Destructive actions не всегда объясняют весь эффект.
10. Локальные изменения и backend sync не объединены одним transaction-like command.
11. Специальные контексты существуют в модели, но не попадают из onboarding.
12. Analytics и selected records могут учитывать нуждающиеся в review/deleted данные недостаточно строго.

### 8.3 Целевая модель

- `PeriodRecord` - единственный источник подтвержденного интервала кровотечения.
- `CycleObservation` не может подменять period record.
- `CyclePrediction` immutable, versioned и никогда не становится фактом автоматически.
- Любая запись проходит через один validator.
- У каждой записи есть revision, server version, source и sync state.
- Нет данных - нет дня цикла, фазы, овуляции, fertile window и Box timing.
- Postpartum/breastfeeding/perimenopause/hormonal context уменьшают или отключают прогноз.

### 8.4 Целевой UX отметки

При нажатии на день:

- Начались месячные.
- Это день месячных.
- Месячные закончились.
- Небольшие выделения.
- Кровотечения не было.
- Изменить существующую запись.
- Удалить с preview и Undo.

Каждый статус должен иметь явную метку:

- Подтверждено вами.
- Предварительный прогноз.
- Общая информация.

## 9. Механика анкеты

Сейчас существуют две разные анкеты, но их роли смешиваются:

1. Onboarding цикла.
2. Box personalization + checkout.

Их нужно разделить.

### 9.1 Анкета цикла должна спрашивать

- цель использования;
- есть ли подтвержденная последняя дата;
- 0/1/2/3-6 прошлых start dates по желанию;
- известная длительность;
- regularity без обещания точности;
- pregnancy/postpartum/breastfeeding/perimenopause;
- hormonal contraception/recent change;
- отдельное согласие на sensitive data;
- отдельное понимание limitations.

Она не должна спрашивать товары или заставлять подписываться.

### 9.2 Анкета Box должна спрашивать

- тип менструального продукта;
- фактическое количество замен в обычный/сильный день;
- ночную защиту;
- applicator/wings/fragrance;
- sensitivity;
- reusable preferences;
- структурированные аллергены и severity;
- продукты, которые нельзя заменять;
- разрешенные substitution rules;
- optional comfort items, все по умолчанию выключены, если не включены тарифом;
- dietary restrictions отдельно от cosmetic/material allergies.

После этого пользователь сохраняет Box profile. Checkout должен быть отдельным коротким процессом.

## 10. LOUSA Box и качество физических товаров

### 10.1 Персонализация

Текущий расчет `periodLength * 4` слишком упрощен. Он не учитывает:

- тип продукта;
- расход в разные дни;
- ночной расход;
- сильные/легкие дни;
- запас;
- остатки прошлого Box;
- reusable mix;
- фактический feedback предыдущего месяца.

Рекомендация должна показывать расчет и позволять изменить количество.

### 10.2 Аллергии и замены

Свободная строка через запятую не является безопасной системой аллергий. Нужны:

- структурированный аллерген;
- область: food/cosmetic/material/fragrance/herbal;
- severity;
- cross-contamination sensitivity;
- запрет замены;
- подтверждение substitution до упаковки.

### 10.3 Честный вердикт по физическому качеству

**Статус: НЕ ПРОВЕРЕНО / P0 BLOCKER для заявлений о премиальном качестве.**

По коду можно увидеть SKU, название, цену и количество на складе. Нельзя доказать:

- кто поставщик и производитель;
- страну происхождения;
- материал/состав;
- absorbency/specification;
- fragrance/chemical declaration;
- lot/batch;
- expiry;
- сертификаты;
- входной контроль;
- условия хранения;
- состояние пломбы;
- кто упаковал;
- разрешенную замену;
- связь жалобы/отзыва с партией.

Минимальная quality system:

- Approved Supplier и SKU Specification.
- Batch/Lot и Expiry на приемке и упаковке.
- Certificates/Documents.
- Incoming inspection и QA release.
- Storage/transport requirements.
- Packing checklist, packer, timestamp, seal.
- Substitution approval.
- Complaint and recall traceability.

Без этого приложение не должно обещать доказанное «высокое качество» содержимого - только дизайн и заявленный подбор.

## 11. Доставка и карта

### 11.1 Сильные стороны

- Встроенная MapLibre карта.
- Полноэкранный выбор с центральным прицелом.
- Debounce reverse geocoding.
- Protection от stale responses.
- Search/location/manual fallback.
- Green success только после backend zone truth.
- Delivery fee принудительно 0.
- Draft сохраняется при ошибке.

### 11.2 Слабые стороны

- Форма слишком длинная.
- Ручной адрес может разойтись с координатами.
- Не каждое изменение гарантированно инвалидирует verified zone.
- Phone validation слабая.
- Leave-at-door details можно сохранить неполными.
- ETA является оценкой зоны, а не подтвержденной capacity.
- Нет полноценного address book UI.
- Live sync с отдельной admin-panel не доказан.

### 11.3 Серверная правда доставки

Backend должен единолично подтверждать:

- `available`;
- `zoneId`;
- `includedInPlan`;
- `deliveryFee = 0`;
- confirmed slot/cutoff;
- saved address revision.

Mobile может хранить draft, но не может самостоятельно показывать «готовится», «в пути» или «доставлено».

Отдельная admin/courier программа должна получать только delivery-safe данные:

- имя;
- телефон;
- адрес;
- координаты;
- окно;
- handoff;
- комментарий.

Данные цикла, симптомов, настроения и приватных заметок не должны попадать в эти payload.

## 12. Приватность и безопасность

Положительное: auth tokens хранятся через SecureStore.

Критическое: health/address state и очереди находятся в AsyncStorage. Это не равно зашифрованному health storage.

Целевая архитектура:

- ключ в Android Keystore;
- encrypted SQLite/MMKV/SQLCipher-подобное хранилище;
- schema version и rollback;
- миграция старых данных;
- optional biometric lock только после Device QA;
- redacted logs;
- отдельные действия «очистить устройство» и «удалить аккаунт»;
- server export;
- server-issued policy versions;
- allow-list полей для support/logistics/courier.

## 16. Definition of Done

Приложение можно считать готовым, только когда:

- Skip onboarding создает ноль menstrual facts;
- ни один путь не принимает future/overlap/impossible period;
- fact и forecast всегда различимы;
- period edit/delete/undo синхронизируются с server revision;
- Box quote/order/payment/subscription существуют на сервере;
- optional/paid item не выбран без явного согласия;
- delivery fee = 0 и includedInPlan подтверждаются сервером;
- address text/coordinate/zone не расходятся;
- separate admin/courier не получают health data;
- чувствительные локальные данные зашифрованы либо ограничение написано честно;
- fake AI отсутствует;
- все элементы проходят touch target/semantics/contrast QA;
- RU/EN/HY проходят screenshot и meaning parity;
- lint/unit/integration/schema/APK/E2E зеленые;
- последний APK проходит полный Device QA;
- каждый физический товар трассируется до supplier/spec/batch/expiry;
- человек без объяснений понимает, где факт, прогноз, исправление даты, Box, оплата и адрес.
